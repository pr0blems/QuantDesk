# QuantDesk V2 数据库字典

数据库名：`binance`。所有业务时间字段统一保存 UTC 时间。Binance API Key 与 Secret 仅保存 Fernet 密文，任何日志和接口响应均不得保存或返回明文。

数据库的既有表和字段已通过 `0010_trading_schema_comments` 写入中文 `TABLE_COMMENT` / `COLUMN_COMMENT`；后续新增字段由各自迁移继续写入中文注释，本字典与数据库内注释共同维护。

`news.source_link_hash` 为 `VARCHAR(64)` 的持久化生成列；当 `link` 非空时，由
`SHA2(CONCAT(COALESCE(source, ''), CHAR(0), link), 256)` 计算。唯一索引
`uq_news_source_link_hash` 在数据库层保证同一来源和原文链接只能保存一次；`link` 为空时该列为空，兼容历史不完整记录。

`0008_mysql_market_store` 创建统一 MySQL/MariaDB 行情与交易存储；`0009_multitenant_trading` 增加租户外键和模拟盘账户层，并将旧的 `kv` 拆分为 `system_state` 与 `user_states`；`0013_news_dedup_hash` 为新闻增加由来源名称与原文链接生成的 SHA-256 唯一去重键，防止旧 MD5 Worker 与新 Worker 在滚动升级期间写入重复文章。模拟盘通过 `(paper_account_id, user_id)` 复合外键保证账户与用户一致；实盘持仓、提醒、模拟持仓、成交和权益查询都必须带租户键。应用不读取本地数据库文件。

## ai_decision_ledger_heads / ai_decision_ledger_records — AI 决策审计链

`ai_decision_ledger_heads` 以 `actor_scope_id` 为主键，保存该租户行为主体的最后序号和最后记录哈希。`ai_decision_ledger_records` 只追加保存提案门禁事件、规范化 UTC 时间、Prompt/模型/输入/输出 SHA-256、脱敏后的规范 JSON、前序哈希及当前记录哈希。

约束：`event_id` 全局唯一，`actor_scope_id + sequence` 唯一；每次追加锁定对应 head 行并原子递增。读取时必须重算每条记录哈希、检查序号和前序哈希连续性，并与 head 对比，从而发现内容篡改及中间/尾部记录删除。表中不保存原始 Prompt、原始行情输入、模型密钥或非法模型原文。

## execution_idempotency_records — 统一执行幂等与恢复日志

该表以完整租户、用户、账户、部署和幂等键生成的 `scope_hash` 为主键，同时保留并复核原始作用域。`intent_json` 保存不可变订单意图；`claim_token` 和 `lease_expires_at` 管理 broker 写入前的独占租约；`checkpoint_json` 在真实写入前保存 Broker、可信 `physical_account_id`、确定性 `clientOrderId`、Preflight 和已批准风险裁决；`result_json` 保存最终完整状态链。`recovery_token`、`recovery_lease_expires_at`、`recovery_started_at` 和 `recovery_epoch` 管理独占恢复所有权，并永久隔离被恢复器接管的原执行 owner。

约束：checkpoint 与 `physical_account_id` 必须同时存在或同时为空。只有尚未产生 checkpoint 的过期 claim 才可被接管；一旦 checkpoint 存在，任何自动重试都被禁止，只能先取得独占 recovery lease，再使用确定性订单号向 Broker 对账。`UNKNOWN -> SUBMITTED -> PARTIALLY_FILLED -> terminal` 只允许成交量不下降的单调推进；旧 owner 和过期 recovery token 均不能回写。所有 JSON 同时保存 SHA-256，读取时必须校验作用域、内容哈希和生命周期状态。升级到 `0032` 前若已有 checkpoint，必须先用可信账户注册信息或交易所稳定 UID 完成映射；迁移会在任何 DDL 前拒绝从账户别名或 API Key 元数据推断物理账户。

## execution_account_controls / execution_quote_watermarks / execution_safety_events — 持久执行安全控制

`execution_account_controls` 以 Broker、市场、可信 `physical_account_id` 和执行模式构成物理控制边界，并通过唯一约束保证同一真实账户不能因租户别名不同而获得第二套预算。租户、用户和 `account_scope` 仍被持久化并逐次复核，但只表达所有权，不能作为物理互斥键。`safe_reason` 与 `kill_reason` 是相互独立的双锁存器：Safe Mode 只允许经过复核的降风险意图，Kill Switch 拒绝全部新授权；释放 Kill Switch 不会清除 Safe Mode。`consecutive_failures`、`version`、`changed_at` 和 `changed_by` 支持跨 Worker 故障累计及乐观并发控制。

LIVE 首次触碰控制行时会钉住 `RiskPolicy + PreflightPolicy + failure_threshold` 的组合指纹；后续进程使用不同策略会 fail closed，并在没有既存人工 Kill Switch 时锁存 `control_policy_mismatch`。账户风险快照同时保存交易所源更新时间、可信抓取完成时间、数据库落库时间、内容哈希和外部引用：任一源时间或观察时间回退都会被拒绝，同一观察时间出现不同内容也会被判为冲突。

`execution_quote_watermarks` 以 `account_control_hash + symbol` 为主键，为每个物理账户、每个标的保存最新报价观察时间、规范哈希和引用。授权事务在安全门和预算裁决之前推进该水位，因此即使本次业务授权被拒绝，也不能再用更旧报价绕过检查；时间回退或同一时间不同价格均会 fail closed。

`execution_safety_events` 只追加保存操作员安全命令。每个命令包含稳定 `command_id`、actor、reason、期望版本以及变更后的双锁状态；同一账户内命令 ID 唯一，命令内容哈希用于拒绝 ID 复用。解除安全锁必须通过 expected-version CAS，成功结果不会自动清除已锁存状态。

## execution_risk_reservations — 原子账户风险预算

该表将每个已授权执行与 `execution_idempotency_records.scope_hash` 一一绑定，保存预留名义敞口、仓位槽位、策略/风险裁决/账户快照哈希、安全状态版本、确定性订单号，以及仓位模式、目标方向/持仓侧、授权前基线数量和授权数量。授权事务按“账户控制行 → execution 行 → reservation 行”统一锁序，在一次提交内完成最终安全门、并发预算检查、风险预留和 checkpoint；提交之前不允许调用 Broker。同一物理账户的同一持仓槽同一时刻只能存在一个活动 reservation，不同持仓槽可以共享同一份真实账户快照。

状态仅允许 `held -> committed_unreflected -> settled`，或在确定零成交拒单/撤单时进入 `released`。UNKNOWN、已提交和部分成交不会按 TTL 自动释放，避免账户快照延迟造成风险预算双花。`settled` 必须提供在数据库中晚于 Broker outcome 落库的真实账户快照，并证明 OPEN 后目标净仓至少增加实际成交量，或 CLOSE/STOP 后目标仓至少减少实际成交量；单向模式出现相反方向并存会视为完整性错误。同一持仓槽不能重复消费同一结算证据，结算后也禁止再接受新的 Broker 状态推进。
