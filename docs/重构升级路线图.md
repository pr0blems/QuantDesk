# QuantDesk 渐进式重构升级路线图

> 状态：阶段 1 完成；阶段 2-4 的新架构基础已落地，存量运行器迁移继续按灰度推进  
> 启动日期：2026-08-05  
> 原则：保持现有 API、数据库和交易行为兼容，以可回滚的小步提交替代一次性重写。

## 1. 目标

QuantDesk 的目标形态是一个以确定性策略和统一执行内核为基础、以 AI 作为研究与决策增强层、支持回测、模拟、Shadow 和实盘逐级发布的多用户量化平台。

本轮重构优先解决四个问题：

1. 回测、模拟和实盘的策略语义不一致。
2. HTTP、持久化、交易所调用和领域规则集中在少数巨型模块。
3. 交易所能力缺少稳定的应用层端口。
4. 周期、风险和运行配置仍存在运行器硬编码。

## 2. 目标依赖方向

```text
interfaces (API / worker / CLI)
             |
             v
application (use cases / ports)
             |
             v
domain (strategy / risk / execution / portfolio)
             ^
             |
infrastructure (database / Binance / Finnhub / AI)
```

依赖约束：

- `domain` 不导入 FastAPI、SQLAlchemy、交易所 SDK 或具体数据库实现。
- `application` 通过 Protocol 使用行情、Broker、仓储和时钟。
- `infrastructure` 实现应用层端口，不向领域层泄漏交易所原始响应。
- `interfaces` 只负责鉴权、输入输出映射和事务边界，不承载交易规则。
- 回测、模拟、Shadow 和实盘共享策略求值与风险裁决，只替换行情源和 Broker。

## 3. 统一运行链路

```text
MarketEvent
  -> StrategyEvaluator
  -> SignalIntent
  -> RiskEngine
  -> ApprovedOrderIntent / RejectedIntent
  -> Broker
  -> OrderEvent / FillEvent
  -> Portfolio / Ledger / Audit
```

所有可执行对象都必须携带：

- 用户、账户和部署标识；
- 由可信账户注册流程取得的物理交易账户标识；
- 不可变策略版本标识；
- 市场、标的和周期；
- 信号时间与有效期；
- 幂等键；
- 风控裁决和可审计证据。

## 4. 渐进迁移规则

1. 先建立公共端口和兼容适配器，再移动旧业务逻辑。
2. 私有跨模块调用必须提升为公共领域能力或删除。
3. 旧 API 在迁移期间保持 URL、状态码和响应结构不变。
4. 不在架构重构中同时改变策略算法；算法变化必须独立版本化。
5. 不在单元测试中发送真实订单或依赖外部网络。
6. 每个阶段必须通过 Ruff、聚焦测试和全量测试。

#### LIVE 切流硬约束

- `physical_account_id` 必须来自可信账户注册信息或交易所稳定 UID，并贯穿 Broker 绑定、execution checkpoint、控制哈希和审计记录。禁止用可轮换的 API Key 哈希、请求参数或 `account_scope` 推导、回退或替代它。
- `account_scope` 只是租户内的意图 ownership alias，用于所有权校验；它不是物理账户互斥键，也不能作为跨部署风险预算和安全状态的隔离边界。物理控制边界至少绑定 broker、market、`physical_account_id` 和 execution mode。
- LIVE 控制策略在物理账户首次使用时 pin `RiskPolicy + PreflightPolicy + failure_threshold` 的组合指纹。相同策略的再次绑定必须是无副作用读取，不能清零连续失败计数或改变版本；策略漂移必须持久化安全 latch 后 fail closed。
- 在 durable OCO/protection group 能原子表达、恢复并对账成对保护单之前，LIVE `TAKE_PROFIT_MARKET` 一律以 `protective_pairing_not_supported` 拒绝且不得写 Broker；`STOP_MARKET` 暂按单一保护槽计数，不得假装已具备 OCO 互斥语义。
- 在 position 单槽模型下，OPEN reservation 未经新账户快照 `observe_account_snapshot` 并 `settle_reflected` 前仍占用槽位，此时 STOP 会被拒绝。未来生产编排必须严格执行“fill → 立即拉取新鲜账户快照 → observe/settle → 安装 STOP”，持续监控未保护窗口；任一步失败都必须进入 safe-close 流程。该编排和监控尚未实现，因此当前统一执行内核不能标记为 live-ready。
- 旧实盘路径只有在上述身份、策略 pin、checkpoint 恢复、账户快照新鲜度、并发预算以及保护组故障演练全部通过后才允许灰度切入统一执行服务。

## 6. 阶段 1 验收条件

- 现有 API 测试不需要改变业务断言。
- 旧策略在未声明周期时仍使用 `4h`，声明周期时按快照读取。
- `paper_engine` 不再导入回测模块的私有信号构建函数。
- 新端口不依赖 FastAPI、SQLAlchemy 或具体 Binance 响应结构。
- Binance 适配器通过假客户端测试，不调用外部服务。
- `ruff check src tests` 和 `pytest -q` 全部通过。
