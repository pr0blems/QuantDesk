# 发现机会模块优化方案

> 项目：QuantDesk NG / `#/ai-monitor`
> 审计日期：2026-08-19
> 范围：发现机会、AI 分析结论、历史机会、预测统计分析，以及相关后端、策略和数据库链路

## 1. 结论摘要

当前系统已经具备一条完整的研究链路：新闻采集与 AI 研判、候选股票映射、技术指标计算、宏观与资金盘口补充、机会门控、预测记录、动态退出和统计分析。它不是“没有底层”，而是已经进入需要做工程收敛和策略校准的阶段。

但系统目前仍不适合直接扩大实盘跟单，主要原因不是页面功能数量不足，而是以下四类问题同时存在：

1. **前端决策密度过高**：机会卡片把行情、宏观、盘口、策略门槛、价格源和持仓信息同时铺开，核心问题“现在能否入场、为什么、风险是什么”不够突出；双列卡片和横向滚动降低了扫描效率。
2. **统计查询路径过重**：预测统计接口会加载全部完成预测，再在 Python 中重建快照、门控、行情和结算证据。只请求 20 条时，线上库只读计时超过 60 秒仍未完成。
3. **策略证据覆盖不足**：六域评分已经存在，但期权、GEX、机构等增强数据覆盖仍低；缺失数据如何降权、阻断和展示尚未形成一套统一且稳定的规则。
4. **数据库写模型与读模型混用**：原始审计 JSON 适合追溯，不适合高频筛选统计。当前统计页反复解析原始证据，导致慢查询、口径复杂和页面等待。

因此，建议先完成 **P0 查询与 UI 收敛**，再做 **P1 数据读模型和任务解耦**，随后才进行 **P2 策略校准与影子盘验证**。不能通过继续增加指标或提高杠杆来跳过这一顺序。

## 3. 当前完整流程与问题位置

```mermaid
flowchart LR
    A["新闻采集"] --> B["AI 新闻分析与 7 天记忆"]
    B --> C["股票与方向候选聚合"]
    C --> D["技术指标扫描"]
    D --> E["宏观/现货/盘口/期权/GEX/机构快照"]
    E --> F["数据质量与风险门控"]
    F --> G["组合评分与入场判定"]
    G --> H["当前机会"]
    H --> I["冻结信号时刻证据"]
    I --> J["预测/影子持仓"]
    J --> K["止盈/止损/移动保护/评分反转退出"]
    K --> L["历史机会与预测统计"]
```

需要重点修复的不是某一个节点，而是三条边：

- `E → F`：增强行情缺失时，评分、阻断和展示口径不完全一致；
- `G → H`：前端没有把“候选、可触发、已触发、数据阻断”压缩成清晰的决策状态；
- `K → L`：统计查询每次从原始证据重新计算，导致慢、难缓存、难核对。

## 4. 前端优化方案

### 4.1 页面信息架构

页面顶部保留三个层级，不再把所有监控细节同时展开：

1. **操作栏**：自动监控、实盘跟单、数据源开关、分析新闻、刷新。
2. **环境摘要栏**：市场时段、开盘倒计时、大盘方向、VIX、数据健康。默认只显示结论；点击展开完整宏观指标。
3. **机会工作区**：当前机会、历史机会、预测统计分析。

当前机会卡片应改为“主结论 + 关键证据 + 展开详情”：

| 首屏必须显示 | 展开后显示 |
|---|---|
| 股票、方向、状态 | 全部策略指标 |
| 是否可入场、唯一主阻断原因 | 宏观评分构成 |
| Binance 当前价格、计划入场区间 | Finnhub/UW 参考与时效 |
| 组合分、新闻分、技术分、资金分 | Option Flow / GEX / 机构证据 |
| 止损、止盈、风险收益比 | 新闻记忆、模型调用、基本面 |
| 数据新鲜度和覆盖率 | 完整门控审计记录 |

### 4.2 状态语义统一

当前“行情降级”“行情缺失”“等待行情”“关键数据缺失”等文案容易和顶部 100% Quote 覆盖冲突。建议统一成五类：

- **候选**：新闻已形成方向，但尚未达到策略门槛；
- **可触发**：核心硬门槛已通过，等待入场价格或下一根确认 K 线；
- **已触发**：已经冻结入场价格并进入预测/跟单生命周期；
- **数据阻断**：缺少必需行情或行情过期，不允许进入；
- **风险阻断**：事件、停牌、价差、来源分歧或宏观风险触发硬门槛。

每张卡片只展示一个主状态和一个主原因；其他原因放入“查看全部门控”。

### 4.3 列表和渲染性能

1. 当前机会和历史机会均由后端分页，默认每页 20 条；禁止前端一次读取 300 条再过滤。
2. 筛选项只在点击“应用筛选”后提交；输入期间不发请求。
3. 每个视图只允许一个有效请求：新请求发出时取消旧请求，并用请求序号避免旧响应覆盖新状态。
4. 初次加载使用骨架屏，后台刷新只更新变化的卡片字段，不清空列表，不闪屏。
5. SSE 消息携带 `entity_id + version + changed_fields`，前端按 ID 合并；30/60 秒轮询仅用于健康兜底。
6. 预测统计表保持服务端分页，长列表使用虚拟滚动或稳定的 20 行分页。
7. 新闻滚动不再使用 80ms 定时器驱动 DOM；改用 CSS 动画或 `requestAnimationFrame`，页面不可见或用户开启“减少动态效果”时暂停。

### 4.4 预测统计页面

统计页拆成四块：

1. **准入结论**：只显示通过项、阻断项和下一步所需数据；
2. **结果概览**：样本数、净胜率、净期望、Profit Factor、最大回撤、长短分布；
3. **筛选器**：默认折叠高级筛选，固定显示日期、股票、方向和状态；
4. **结果表**：显示信号、入场、退出、成本后收益、MFE/MAE、退出原因、证据版本。

加载状态必须区分：

- 首次读取；
- 后台刷新（保留旧数据）；
- 筛选无结果；
- 请求失败；
- 数据版本不兼容。

### 4.5 前端验收标准

- 1440px 宽度下无页面级横向滚动；
- 当前机会首屏可在 5 秒内判断“方向、是否可入场、价格、风险、阻断原因”；
- 当前机会接口 P95 小于 800ms，统计接口 P95 小于 2s；
- 后台刷新不清空 DOM，不出现整页闪烁；
- 日期、方向、股票、退出原因筛选可重复、可分享、刷新后保持；
- 屏幕阅读器可识别按钮、状态和表格表头，颜色不是唯一状态表达方式。

## 5. 后端优化方案

### 5.1 拆分领域服务

将 `ai_monitor.py` 拆成独立服务，先迁移不改行为：

```text
ai_monitor/
  news_pipeline.py          新闻候选与记忆
  candidate_service.py      股票/方向聚合与去重
  market_feature_service.py 行情、宏观、盘口与增强数据
  scoring_service.py        评分和权重版本
  gate_service.py           入场硬门槛与阻断原因
  prediction_service.py     预测生命周期
  settlement_service.py     退出与结算
  analytics_service.py      统计读模型
  event_service.py          SSE/outbox 事件
```

API 层只做参数校验、权限和序列化，不在请求线程中执行全量历史重建。

### 5.2 机会接口改造

建议新增稳定的查询协议：

```http
GET /api/v2/ai-monitor/opportunities
  ?scope=current|history
  &state=all|triggered|triggerable|candidate|data_blocked|risk_blocked
  &direction=all|long|short
  &page=1&limit=20
  &sort=discovered_at_desc
```

响应增加：

- `total`、`page`、`pages`；
- `server_time`、`data_version`；
- `status_summary`；
- `primary_blocker` 与结构化 `gate_checks`；
- `quote_freshness_ms` 与 `coverage`；
- `etag` 或记录 `version`，支持增量更新。

实时价格只从缓存或最新快照批量读取，不允许每张卡片分别调用外部源。

### 5.3 预测统计改造

当前最优先的后端问题是：**统计接口先读取全部已完成预测，再逐条拼装门控、快照、Finnhub 和增强特征，最后才分页。**

改造为两条路径：

1. **明细查询**：只查询当前页的事实表，SQL 完成日期、方向、评分、版本和退出原因过滤；
2. **汇总查询**：对事实表做聚合，结果按筛选条件缓存 30–60 秒；准入报告独立接口加载。

禁止在明细请求中：

- 重新结算；
- 回查外部行情；
- 为全部历史记录解析大型 JSON；
- 同步计算 readiness、消融实验和筛选结果。

### 5.4 异步任务与幂等

- 新闻分析、机会扫描、结算、读模型刷新分别作为任务；
- 使用数据库租约或 Redis 锁保证同一任务只有一个主实例；
- 每个任务有 `run_id`、`idempotency_key`、开始/结束时间、输入数量、输出数量和失败原因；
- 写入业务表和发送 SSE 事件通过 outbox 保证一致；
- 外部接口使用限流、熔断、退避和最后成功快照，不能把外部超时拖入页面请求。

### 5.5 可观测性

至少补充以下指标：

- 新闻采集到分析完成的 P50/P95；
- 新闻分析到机会生成的 P50/P95；
- 各门控阻断数量与比例；
- 各数据源新鲜度、成功率、限流次数；
- 当前机会查询和统计查询 P50/P95/P99；
- 预测创建、待结算、已结算、不可结算数量；
- 机会数、预测数和统计事实数的一致性差异。

## 6. 策略优化方案

### 6.1 将“候选评分”和“入场触发”分离

组合分只用于排序，不应单独决定买入。完整入场流程应为：

1. 新闻产生股票、方向、时效和置信度；
2. 去重并聚合 7 天记忆，判断新事件是增强、削弱还是反转；
3. 技术策略组满足最小同向条件；
4. 行情质量、市场时段、事件风险等硬门槛通过；
5. 组合分达到该方向、该时段的阈值；
6. 价格进入计划入场区间或新 K 线完成确认；
7. 冻结入场证据、价格、止损、止盈、版本后，才进入“已触发”。

### 6.2 六域评分与缺失数据政策

当前发布策略已存在六域权重：

| 领域 | 当前发布权重 |
|---|---:|
| 新闻与历史研判 | 20% |
| 技术指标 | 30% |
| 宏观与板块环境 | 10% |
| 期权资金流 | 20% |
| GEX | 10% |
| 机构流 | 10% |

需要明确三类证据：

- **核心必需**：Binance 主行情、K 线、时钟、停牌/重大事件。缺失即阻断；
- **可降级**：Finnhub/UW 对照价格。缺失不伪造中性分，降低置信度并标记；
- **增强证据**：Option Flow、GEX、机构流。只有新鲜且覆盖达标才参与权重；否则按版本规则重归一化，不得填 50 分。

UI 必须显示该条机会实际生效的权重，而不是固定写死旧版的 45%/25%/30%。历史记录必须显示信号时刻的 `weights_version`、`feature_version` 和 `decision_version`。

### 6.3 分时段和多空校准

盘前、盘中、盘后和闭市快照的数据含义不同，应分别建立阈值：

- 盘前：新闻和缺口预期为主，降低盘口权重，必须等待开盘确认才能自动跟单；
- 盘中：允许使用盘口、成交和增强数据，触发阈值可以动态校准；
- 盘后：只生成次日候选，不直接按延迟参考价作为实盘入场；
- 闭市：明确显示为研究候选，不应显示“等待实时行情”造成故障误解。

做多和做空必须分别统计胜率、净期望、MFE/MAE、板块和时段表现，禁止用总体胜率掩盖单方向失效。

### 6.4 退出策略

预测生命周期不能只靠一小时到期。建议保留五种结构化退出：

1. 硬止损；
2. 固定或 ATR 止盈；
3. 盈利保护与移动止盈；
4. 组合分跌破或方向反转；
5. 最大持有期限兜底。

所有退出都需要保存：触发时间、触发价格、触发规则版本、MFE、MAE、成本前后收益。最大持有期限只是兜底，不应被展示为“自动止盈/止损”。

### 6.5 准入标准

在扩大自动实盘前，至少满足：

- 有效且可重放样本不少于 1,000 条；
- 跨度不少于 180 个自然日，并覆盖高波动、低波动和重大事件日；
- 长、短方向各不少于 100 条；
- 成本后 Profit Factor ≥ 1.20；
- 成本后平均收益 95% 置信区间下界大于 0；
- 双倍手续费和滑点压力测试后仍为正；
- 单品种和单板块集中度在设定上限内；
- 至少 4 周影子盘无数据对账和结算事故。

这些门槛只能降低风险，不能保证盈利。

## 7. 数据库调整方案

### 7.1 保留原始审计表，新增统计事实表

现有机会、预测、行情快照和门控决策继续作为不可变审计证据。新增一个面向查询的事实表，例如 `ai_monitor_prediction_facts`：

```text
id, user_id, opportunity_id, prediction_id
symbol, contract_symbol, direction, timeframe
signal_at, entry_at, exit_at, settled_at
opportunity_status, prediction_status, result, net_result
market_session, quote_quality, event_risk, data_coverage
news_score, technical_score, market_context_score
option_flow_score, gex_score, institutional_flow_score
market_flow_score, combined_score
entry_price, exit_price, gross_return_bps, net_return_bps
mfe_bps, mae_bps, estimated_cost_bps, exit_reason
weights_version, feature_version, decision_version, settlement_version
snapshot_complete, invalid_reason, created_at, updated_at
```

该表由结算任务和对账任务更新，不由统计接口临时拼装。

### 7.2 评分历史与当前状态

门控记录目前已超过 16,000 条，适合审计但不适合直接画每张卡片的趋势。新增：

- `ai_monitor_opportunity_current`：每个机会一行，保存最新状态和最新评分；
- `ai_monitor_score_history`：按机会、扫描时间保存各域分数和主阻断原因；
- 可按 5 分钟采样，连续不变化的扫描只更新心跳或做压缩，避免重复记录。

### 7.3 索引建议

```text
ai_monitor_opportunities:
  (user_id, status, discovered_at DESC)
  (user_id, contract_symbol, status, expires_at)

ai_monitor_predictions:
  (user_id, status, due_at)
  (user_id, predicted_at DESC)
  (user_id, symbol, predicted_at DESC)

ai_monitor_prediction_facts:
  (user_id, signal_at DESC)
  (user_id, prediction_status, signal_at DESC)
  (user_id, direction, net_result, signal_at DESC)
  (user_id, market_session, signal_at DESC)
  (user_id, feature_version, decision_version, signal_at DESC)
  (user_id, symbol, signal_at DESC)

ai_monitor_score_history:
  UNIQUE (opportunity_id, sampled_at)
  (opportunity_id, sampled_at DESC)
```

JSON 字段继续保留原始证据，但经常筛选的字段必须扁平化为数值或枚举列。

### 7.4 数据生命周期和一致性

- 高频原始流按月份分区或归档；保留 30–90 天全量，长期保存 5/15 分钟降采样；
- 每次迁移前备份线上库，并记录迁移批次；
- 对历史 468 条预测执行一次版本化回填，不修改原始证据；
- 无法构造完整信号时刻快照的早期记录标记 `snapshot_complete=false`，只用于参考，不纳入严格准入；
- 每日对账：机会数、预测数、待结算数、事实表数和无效数必须守恒；
- 禁止物理删除历史错误数据，改用 `invalid_reason` 隔离，避免后续无法解释统计变化。

## 8. 开发顺序

### P0：立即修复（3–5 个开发日）

- 统计明细先分页再读取，readiness 和消融数据拆成独立请求；
- 当前/历史机会改服务端分页与状态筛选；
- 卡片收敛为主状态、主阻断、价格和风险，详情按需展开；
- 修复全页横向滚动、加载竞态、整页闪烁和筛选期间自动请求；
- UI 按信号版本显示实际生效权重。

验收：统计页 20 条查询 P95 < 2s；当前机会 P95 < 800ms；页面无横向滚动和全量闪烁。

### P1：读模型和任务解耦（5–8 个开发日）

- 新增预测事实表、当前机会表和评分历史表；
- 增加必要索引和回填脚本；
- 将统计、准入和消融拆分成独立服务；
- 增加任务幂等、租约、outbox 和数据对账；
- 上线 API 延迟、数据覆盖和阻断原因监控。

### P2：策略校准（1–2 周）

- 分离候选分和触发门控；
- 完成六域缺失数据政策；
- 分时段、分方向、分板块校准阈值；
- 调整自适应止盈止损、移动保护和评分反转退出；
- 通过影子盘积累稳定的信号时刻快照。

### P3：准入验证（持续至少 4 周）

- 样本外和滚动窗口验证；
- 双倍成本压力测试；
- 监控集中度、最大回撤和策略漂移；
- 达到准入门槛后，仅对白名单品种和小额度分阶段开启跟单。

## 9. 需要你提供或确认的事项

以下事项会直接影响实现，不建议由开发侧自行假设：

| 事项 | 需要确认的内容 | 当前建议 |
|---|---|---|
| 主交易行情 | Binance 映射合约是否始终作为入场、退出和结算主价格 | **是**；Finnhub/UW 仅作参考、质量校验和增强证据 |
| 可交易时段 | 是否允许盘前/盘后自动实盘 | 第一阶段仅允许美股常规盘；盘前盘后只生成候选 |
| 风险预算 | 单笔风险、单日亏损、总回撤、最大持仓、单板块敞口 | 需要给出最终硬上限 |
| 成本模型 | 手续费、滑点、资金成本和杠杆 | 提供真实账户费率；统计默认必须使用成本后结果 |
| 数据源权限 | Finnhub、Unusual Whales 套餐可用接口和频率 | 提供账户后台可见的权限清单，不要在聊天中发送密钥 |
| 品种白名单 | 哪些 Binance 美股映射合约允许自动跟单 | 第一阶段只选流动性和行情质量稳定的 10–20 个 |
| 准入目标 | Profit Factor、最大回撤、净期望、置信下界 | 采用本文件 6.5 的最低门槛，若更严格请确认 |
| 线上变更窗口 | 数据库迁移、回填和短暂停机时间 | 提供一次可备份、可回滚的维护窗口 |
| 验收负责人 | 谁确认 UI、策略和实盘风险三类验收 | 建议分别指定产品、策略、运维/风控验收人 |

你这边最关键的帮助不是继续补页面需求，而是确认上表前四项：**主行情口径、允许交易时段、风险硬上限、真实成本模型**。这四项确认后，P0 与 P1 可以直接进入开发，P2 的策略结果才有统一验收标准。
