# QuantDesk NG 项目开发计划

> 计划版本：1.0  
> 原则：以可验证的风险降低为先，不以功能数量或模型宣传替代验收。

## 1. 计划目标

在不突破“默认不自动实盘”的安全边界下，先将本地私人部署提升为稳定、可解释、可恢复的量化研究与模拟执行平台；再按真实验证结果决定是否进入实盘和 SaaS 阶段。

## 2. 里程碑路线图

| 阶段 | 目标 | 主要交付物 | 完成判定 |
|---|---|---|---|
| M0：运行可信 | 固化部署与可观测性 | 启动/停止脚本、备份恢复脚本、日志目录规范、健康/指标仪表盘、CI 结果通知 | 重启后 API、数据库、4 Worker 自动恢复；演练一次备份恢复 |
| M1：数据可信 | 保障近实时数据与来源质量 | 数据新鲜度 SLA、缺失/延迟告警、供应商状态、行情与美股窗口对齐回归集 | 断流、旧数据、错误映射均可被 UI 和指标识别 |
| M2：预测可信 | 让预测可验证而非只可展示 | 5m/15m/1h/2h/4h 前瞻账本、滚动校准报告、漂移告警、多源证据面板 | 任何展示方向均可回溯；未达门槛模型自动观望 |
| M3：策略可信 | 完成策略到模拟盘的可审计闭环 | 异步三阶段优化器、交叉验证、进度事件、参数提案、模拟盘回放 | 候选由真实回测产生；批准/回滚可复现 |
| M4：网络与体验 | 增强大陆网络可用性和操作效率 | 代理测速历史、订阅刷新、失败回退提示、关键页面响应式/E2E | 真实订阅下代理失败不造成数据静默中断 |
| M5：受控实盘评审 | 只准备，不默认开放 | 条件单/止损、对账、Kill Switch、Outbox、Shadow/Canary 报告 | 所有交易安全门通过后，由用户显式批准极小额 Canary |
| M6：商业化扩展 | 在私人稳定后再开放 | 商户接入、订单/回调、套餐管理、对外 API 限流和租户隔离审计 | 支付和账务通过沙箱与安全评审，绝不以 feature flag 冒充上线 |

## 3. M0 — 运行可信（最高优先级）

### 工作项

1. 为 MariaDB 建立定时逻辑备份、恢复演练与保留策略；备份中不得包含日志里的敏感数据。
2. 为 API 与四类 Worker 增加统一运行面板：存活、最近心跳、延迟、失败次数、队列/任务积压。
3. 在 GitHub CI 中固定 Python/Node/数据库版本，启用 MySQL/MariaDB 集成测试；发布门禁读取受保护变量但不打印值。
4. 定义异常处理手册：数据库不可用、Binance 限流、代理失效、新闻源失效、Worker 重复租约和模型失败。

### 验收

- 断开一个 Worker 后，系统在明确时间内识别、告警并恢复，且不会生成重复交易动作。
- 从备份恢复到隔离实例后，迁移版本、用户、策略、模拟盘和审计表完整可读。
- CI 在 pull request 上给出明确的通过/失败结果，而非仅依赖本机测试。

## 4. M1 — 数据可信

### 工作项

- 为每条监控数据统一记录 `source_timestamp`、`received_at`、延迟、覆盖率和失败原因。
- 对 Binance 合约与美股映射维护人工可编辑的映射表、市场状态和不可直接比较提示。
- 为新闻和宏观事件加入来源等级、交叉印证数、事件时间与失效期；把翻译文本和原始事实分离。
- 对代理节点记录端到端测试结果与趋势，优选逻辑仅选择健康、低延迟节点。

### 验收

- 任何数据卡片能显示“数据来自哪里、何时采集、是否过期”。
- 数据质量不足时预测/模拟动作进入阻断或降级状态，前端有明确原因。

## 5. M2 — 预测可信

### 工作项

1. 固化每个周期的标签定义、入场价格、费用、点差和结果结算逻辑。
2. 每日生成滚动准确率、覆盖率、Brier、校准曲线、分标的/分波动状态统计。
3. 接入多提供商时采用独立超时、失败隔离和成本上限；每个 vote 都必须携带模型版本、证据和有效期。
4. 引入 champion / challenger：新模型先 shadow，再满足样本与校准门槛后人工批准。

### 验收

- “75%”只允许在锁定样本、明确预测对象、样本数量和置信区间都展示时出现。
- 任一未批准或数据不足模型都不能影响模拟盘开仓信号。

## 6. M3 — 策略与模拟执行可信

### 工作项

- 实现可恢复的三阶段优化任务：粗筛、深搜、时间序列交叉验证；任务进度通过 WebSocket/轮询输出。
- 将优化候选与策略版本、回测数据集版本、费用假设、随机种子绑定。
- 补齐模拟盘订单状态机、止损触发路径、资金费、滑点/流动性模型和异常回放。
- 建立每日策略健康检查：回撤、成交偏差、数据缺失、预测漂移触发重新评估，不自动改参数。

### 验收

- 用户可从一次模拟成交追溯到策略版本、预测、行情特征、风险规则和费用。
- 任何参数变更必须经过提案与审批；回滚能恢复确定版本。

## 7. M4 — 代理、UI 与 E2E

### 工作项

- 完善 `/proxy`：订阅刷新、测速历史、筛选、健康趋势、自动选择依据和回退原因。
- 在保留合约条状布局的前提下，统一每行的数值对齐、字体自适应、方向高亮和美股对照区。
- 为登录、监控、自选、代理、回测、模拟盘和权限边界建立浏览器 E2E 冒烟测试。

### 验收

- 典型桌面分辨率和移动宽度下信息无截断、无错位；未登录访问受保护页面会明确跳转登录。
- 代理不可用时显示直连回退和风险，而非无提示地静默失败。

## 8. M5 — 自动实盘的准入门槛

本阶段不是默认开发授权。只有在用户显式批准后，且以下全部完成，才可开始：

- Binance API 权限、IP 白名单和账户类型已逐项核验；
- 下单、条件止损、撤单、仓位/订单/余额对账具备幂等键与重试边界；
- Kill Switch 可在 API、Worker 和交易所订单三个层面停止风险敞口；
- Shadow 至少覆盖约定的市场状态与异常场景；
- Canary 金额、最大仓位、最大日损、人工值守和回滚负责人书面确认。

## 9. 决策与外部依赖清单

| 依赖 | 需要的用户/外部动作 | 不具备时的系统行为 |
|---|---|---|
| Binance API | 在新系统录入或提供可恢复的旧主密钥；核验权限和 IP | 只运行公开行情、研究与模拟盘 |
| AI 提供商 | 提供 API Key、模型名单、预算与可接受数据范围 | 使用规则/已验证模型；不伪造多模型结论 |
| 代理订阅 | 提供合法订阅或节点、网络用途与策略 | 直连或显示代理未配置 |
| Mihomo | 明确二进制来源、版本、许可与端口策略 | 不启动系统代理进程 |
| 支付 | 商户资质、密钥、回调域名、退款规则 | 保持 `payment_available=false` |
| 生产部署 | 域名、TLS、数据库备份、监控接收方 | 仅作为本地/私人部署运行 |

## 10. 每个阶段的交付纪律

每项功能完成时必须同时提交：代码、迁移（如涉及数据库）、单元/集成测试、运行/回滚说明、风险说明和更新后的进度文档。没有可执行验收证据的功能，一律标记为“部分完成”，不以界面展示或占位接口计入完成。
