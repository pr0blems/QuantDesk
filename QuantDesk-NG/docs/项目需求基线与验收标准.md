# QuantDesk NG 项目需求基线与验收标准

> 文档版本：1.0  
> 基线日期：2026-08-06  
> 适用分支：`main`  
> 事实来源：`测试项目需求文档.md`、`需求确认书.md`、运行代码、迁移与自动化测试。

## 1. 产品定位与优先级

QuantDesk NG 是面向 Binance USDⓈ-M / TradFi 永续合约的量化研究、监控、预测和受控模拟执行系统。它的核心价值不是承诺收益，而是把行情、新闻、策略、预测、回测和模拟盘串成可追溯闭环。

当前以**私人部署、近实时不断流、预测可信度和系统稳定性优先**为默认产品口径。多租户 SaaS、支付和对外开放 API 作为可扩展能力保留，但不应挤占交易数据质量、风险门控和运行可靠性的优先级。

优先级顺序：

1. 行情、预测和模拟执行的连续性、可观测性与数据质量；
2. 预测结果的校准、前瞻验证和可解释性；
3. 策略回测、参数优化和人工审核闭环；
4. 代理可用性与 Binance 连通性；
5. SaaS、支付、模型市场等商业化能力。

## 2. 不可妥协的业务与安全边界

- 默认只允许监控、研究、回测和模拟盘；`LIVE_EXECUTION_ENABLED` 被代码锁定，未完成交易所侧止损、对账、Kill Switch、Outbox、影子盘和极小额 Canary 验收前不得开放自动实盘。
- 任何预测都是概率和证据结论，不得展示为收益承诺，不得因未校准模型自动开仓。
- Binance、代理、AI 模型等密钥仅以加密密文保存；接口、日志、审计元数据和前端不得回显明文。
- 预测数据不足、来源过期、模型未通过发布门槛或多源意见不足时，系统必须返回 `observe` / `neutral` / `insufficient_evidence`，而不是强行给出方向。
- 模拟盘必须以 Binance 合约规则、费率、最小变动、资金费和可获得的交易所参数为准；无法实时取得的交易所参数必须标注来源和时间，而不是静默猜测。

## 3. 目标闭环

```text
Binance 行情 / 订单簿 / 持仓指标 / 新闻 / 美股映射
                    ↓（质量、时效、来源校验）
特征快照 → 多周期预测 / 多空博弈 → 前瞻结果账本与校准
                    ↓
策略模板 / AI 辅助编辑 → 回测 → 参数候选 → 人工提案审批
                    ↓
模拟盘执行 → 风险、止损、成交与费用反馈 → 再训练 / 再优化
```

每个箭头都应保存输入版本、时间戳、质量状态与审计记录，使用户能回答“为何给出此结论”“用的是什么数据”“事后是否正确”。

## 4. 需求模块与验收标准

| 模块 | 目标能力 | 最低验收标准 |
|---|---|---|
| 账户与凭据 | 多用户、JWT、管理员、Binance/AI 凭据加密与审计 | 明文不入库、不回显；权限隔离；凭据更新可审计 |
| 合约监控 | Binance TradFi / USDⓈ-M 近实时行情、异动高亮、30 分钟多空力量、自选置顶、美股对应信息 | 行情断流可识别；时间窗口与合约数据对齐；异常数据不伪装为实时 |
| 信息源 | 官方、交易所、宏观、加密新闻、市场微观结构 | 来源分级、去重、时间有效性和质量标签；低质量新闻不得驱动交易 |
| 预测与博弈 | 5m、15m、1h、2h、4h 多周期概率、证据投票、校准与结果回写 | 概率可校验；至少两个独立新鲜来源才允许共识；未批准模型被排除 |
| 策略中心 | 模板、版本、DSL、安全的 AI 辅助编辑、信号解释 | 策略不可执行任意代码；版本可追溯；信号包含入场/退出/风险依据 |
| 回测与优化 | 真实历史数据回测、候选参数、提案、审批与回滚 | 候选必须绑定同用户已完成回测；少样本或指标不完整不得被采纳 |
| 模拟盘 | 以实际合约规格、费率、最小数量和风险规则为基准的受控执行 | 止损/止盈/手续费/资金费有明确账本；错误与拒单可解释 |
| 代理 | Clash YAML/Base64 导入、HTTP/SOCKS5 测试、自动选优与直连回退 | 订阅原文及密码不明文保存；节点失效不阻断行情采集；状态可见 |
| 运维 | 原生 Windows 本地部署、迁移、健康检查、Worker 租约与指标 | API、数据库、4 个 Worker 可独立报告健康；失败可定位日志 |
| SaaS 扩展 | 套餐、配额、外部 API、支付接口边界 | 支付未接入前必须明确 feature-gated；不可把人工套餐变更描述成真实收款 |

## 5. 数据与模型验收门槛

1. **数据新鲜度**：行情、订单簿、持仓、新闻分别记录采集时间；超过对应窗口时预测进入降级或阻断状态。
2. **前瞻验证**：预测先写入不可变账本，再在目标周期结束后计算方向准确率、Brier 分数和校准偏差；禁止使用未来数据回填。
3. **模型发布**：只有样本量、方向准确率、Brier 分数、校准偏差同时通过门槛的模型版本才可被批准；批准、拒绝、回滚均有审计。
4. **优化可信度**：参数空间受限并校验步长；候选的排名来自已完成回测指标，不允许手工伪造分数。
5. **模拟与实盘隔离**：模拟盘仓位、成交和风险账本不得调用实盘下单通道；未来开启实盘必须先通过独立的 Canary 计划。

## 6. 当前范围外或依赖外部条件的需求

- 真实自动实盘下单、交易所侧条件单、对账和故障恢复；
- Mihomo 内核的下载、授权、进程管理和系统级代理接管；
- 真实微信/支付宝收款、订单签名、回调验签、退款和发票；
- 真实代理订阅、AI 服务商、Binance API Key 的录入与授权；
- 生产域名、HTTPS、数据库 TLS、监控告警接收方与备份恢复演练。

这些项目不是“代码写完即可上线”的事项，必须取得相应凭据、商户资质、网络条件或运维授权后，按验收门槛逐项启用。

## 7. 需求变更规则

- 任何影响交易、费用、风险、数据源或模型阈值的变更，必须同时更新本文件、测试和审计说明。
- UI 优化不得改变监控条状布局中既有的数据语义；美股信息必须在对应合约行下按相同统计窗口展示。
- 若需求文档与运行代码冲突，以“安全边界 + 已验证代码行为”为准，并在开发进度中记录差距，不能通过文档宣称未实现能力。
